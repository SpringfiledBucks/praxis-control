# 整改与服务优先路线：Web、Windows 小组件和大模型

状态：ACCEPTED（交付优先级与保护边界） / PROPOSED（具体云平台与模型供应商）

日期：2026-07-31

## 1. 本轮判断

下一阶段不继续扩展完整 Windows/Linux GUI。交付主线调整为：

1. 修正日常输入、周复盘和结果校准中的事实边界；
2. 把同一套服务端与 Web 完整入口分别做成可复现的本机轻量部署和标准云端部署；
3. Windows 11 小组件作为 Web 的薄入口并行规划，不复制业务规则；
4. 开始规划大模型接入，但先运行影子建议，不让模型直接形成正式事实、硬门槛或外部动作。

“双端”在本计划中指两个部署档案，而不是两个可同时写入的事实库：

- 本机端：PGlite、动态回环端口、单用户 Web/API；
- 云端：OCI 应用容器、独立 PostgreSQL、HTTPS 反向代理、单一权威事实源。

两端共用领域规则、迁移、Web 页面、JSON API 和审计语义。轻量库与云端库不做长期双向复制；切换仍是备份、导出、空库导入、对账和人工确认。

## 2. 整改优先级

### P0：周复盘事实边界

当前实现把“最近七天”统计保存到自然周标识，对自由文本矛盾/瓶颈取众数，并通过页面隐藏字段回传统计值。整改要求：

- 明确区分自然周和滚动七天；首版采用自然周，查询使用闭区间起点和开区间终点；
- 保存时由服务端按 `week_start` 重新计算事实摘要，不接受客户端提交的计数和平均值作为权威输入；
- 不再对自由文本取众数，主要矛盾和瓶颈使用项目/知识节点稳定 ID 聚合；
- 用户可以修改周复盘统计，但修改不得覆盖系统计算快照。

周复盘保存两层结果：

```text
computed_snapshot  系统根据正式记录计算的原始统计
manual_adjustments 用户修改后的字段、原值、新值和修改原因
reported_snapshot  展示与报告采用的最终值
```

计数、平均值等派生事实允许用户调整，但必须填写原因并追加审计事件；源记录后来被修正时重新计算 `computed_snapshot`，保留原人工调整并提示重新确认。主要矛盾、瓶颈、证据变化、组合调整和下周目标属于解释性判断，继续由用户直接编辑。

### P0：取消伪精确和默认高分

- 日常贡献、证据、精力和注意力从 0–10 滑块改为语义分类；
- 旧数值字段暂时保留为内部映射和迁移兼容，不再作为默认交互；
- 移除日常 `8/8/6` 和结果复盘 `7/7` 的默认高分锚定；
- 项目已有的阶段目标、主要矛盾和瓶颈由日常决策引用，只有变化时才编辑；
- 高风险授权、损失承受和恢复路径仍是独立硬门槛。

### P0：补足实际结果和余额校准

结果复盘新增实际投入、交付状态、停止条件命中、瓶颈变化和新增证据。系统用预计与实际差值形成个人校准历史，输出时间区间和适合的任务类型，不生成一个总余额分。

### P1：证据与图谱

- 证据成为正式知识对象，记录来源、时间、支持/反驳关系、可复现性、独立性和时效性；
- 区分决策时的 `expected_strength` 与复盘后的 `observed_effect`；
- 图谱优先回答“瓶颈由什么支持”“哪些决策没有产生预期改善”“哪些假设被结果反驳”，再增加纯视觉功能；
- 多候选或重大决策才触发替代方案、支配关系、场景和 FMEA，不进入普通每日表单。

## 3. 服务端与 Web 的标准部署路线

### 3.1 共同应用边界

- 浏览器、小组件、CLI/TUI 和未来客户端都只调用版本化 API；
- PGlite/PostgreSQL 只由应用服务访问；
- Web 是完整入口，小组件只显示摘要和深链接；
- 正式写入经过 Schema、事务、领域规则、规则版本和追加审计；
- 部署档案改变存储、认证和运行方式，不改变业务语义。

### 3.2 本机轻量档案

继续保留当前 PGlite、动态回环端口、运行状态文件和安全关闭。下一阶段只补充：

- 有界日志轮换；
- Web/PWA manifest、图标和离线/失联页面；
- 本机数据备份提醒与升级前检查；
- 与云端部署相同的 API 能力声明。

动态端口意味着安装型 PWA 和 PWA 小组件不能可靠绑定本机 origin。因此 Windows 小组件第一阶段只连接稳定 HTTPS 云端；本机小组件若未来确有需求，再由已打包的 Windows 提供程序读取运行状态并转发到本机 API。

### 3.3 云端全量档案

首个标准云部署以单节点、单应用副本为基线，不立即引入 Kubernetes。应具备：

- 可移植 OCI 镜像，使用正式 Node.js 运行时基础镜像，不再把 Gitea 镜像作为应用基础镜像，也不把单一地区的软件源写死在公共构建中；
- 应用容器无状态，PostgreSQL 是唯一持久事实源；
- 数据库不发布公网端口，应用只通过内部网络使用最低权限角色访问；
- HTTPS 反向代理是唯一外部入口，覆盖转发头、限制请求体并禁止缓存受保护页面；
- 密码、会话密钥和模型密钥使用平台 Secret 或只读 secret 文件，不写入镜像、源码、日志或页面；
- 区分存活检查与就绪检查；就绪检查必须验证数据库和迁移版本；
- 数据库迁移改为部署前一次性任务，不能由多个应用副本并发自动运行；
- 镜像使用不可变版本或摘要，升级包含数据库备份、迁移预检、健康验证和应用回滚路径；
- 定时备份、异机保存、恢复演练、表级计数和审计链校验进入发布门槛；
- 先保持单副本。登录失败限速目前是进程内状态，多副本前必须移到可信反向代理或共享存储。

标准交付物按顺序为：

1. `compose` 单节点参考部署和完整 preflight；
2. Gitea 构建、测试、生成带版本的 OCI 镜像；
3. 独立临时域名/证书环境验收；
4. 备份与恢复演练；
5. 明确现有数据库消费者并收敛非预期的 5432 暴露；
6. 完成轻量数据导入对账后，才允许切换权威事实源。

具体云厂商、域名、证书来源和托管 PostgreSQL 供应商仍为待选项，不在本计划中预设。

## 4. Windows 11 小组件路线

微软当前允许以已打包 Win32 应用或 PWA 实现 Windows 小组件。由于完整客户端暂缓，第一阶段采用 PWA 小组件验证路线：

- Web 增加 PWA manifest、service worker 和专用小组件定义；
- 小组件使用独立的 Adaptive Card/小组件布局，不能直接嵌入现有完整页面；
- 首版只显示今日主行动、剩余可用时间区间、待复盘数量、WIP 和服务状态；
- 操作以打开对应 HTTPS Web 深链接为主；不在小组件中执行高风险动作、管理密钥或直接写数据库；
- 增加只返回最小必要字段的 `GET /api/widgets/summary`，不得复用包含不必要私人内容的完整工作台响应；
- 未登录、会话过期、网络离线和服务不可用必须显示可恢复状态，不缓存敏感正文；
- 验收覆盖 Windows 11、小/中/大尺寸、明暗主题、键盘/屏幕阅读器、会话过期和点击深链接。

Windows 全部交付物同时遵守以下安全软件兼容边界：

- 不要求关闭、暂停或降低 Microsoft Defender、SmartScreen、Windows 防火墙或第三方安全软件；
- 不要求用户添加目录、进程、端口或文件类型排除项，也不以全局降低 PowerShell 执行策略作为安装步骤；
- 小组件和 Web 只使用标准 HTTPS 出站访问，不为普通用户创建入站防火墙放行规则；
- 公开测试版继续提供 SHA-256，但哈希不能替代发布者签名；进入稳定 Windows 分发前完成受信任代码签名，并评估 MSIX/PWA 商店或等价可信分发；
- 安全产品拦截时保持失败状态，显示包版本、签名/哈希检查和不含隐私的诊断路径，不提供绕过或关闭保护的教程；
- Windows 验收环境保持系统安全功能启用，并把误报、信誉和签名验证作为发布门槛。

若 PWA 小组件在目标 Windows 版本、Edge 分发或认证行为上不能稳定验收，再启用已打包 Win32 提供程序；它仍只调用 API，不恢复完整 Windows GUI 业务开发。

## 5. 大模型接入规划

现在可以开始规划和建立接口，但不能直接把大模型放入正式决策链。首批适用能力：

- 从自然语言提取候选项目、行动、交付物、停止条件和证据引用；
- 根据稳定项目关系建议“无关/间接/直接”和证据成熟度，并给出依据；
- 起草周复盘、归纳重复偏差和生成待确认的图谱关系；
- 用自然语言查询已有事实和审计记录；
- 解释触发的确定性规则。

禁止范围：

- 模型不能决定 `BLOCKED` 硬门槛、授权状态或损失是否可承受；
- 模型输出不能静默写入正式事实库、修改历史或执行外部动作；
- 模型不能把自然语言直接变成不可解释的权威分数；
- 浏览器和小组件不得持有模型供应商密钥；
- 默认不得向外部模型发送完整数据库、审计链、凭据、内部地址或无关私人文本。

### 5.1 建议架构

```text
Web/API 请求
  -> Context Builder（按记录 ID 白名单取数、脱敏、限长）
  -> Model Gateway（供应商中立接口、超时、重试和预算）
  -> JSON Schema 校验
  -> Advisory Result（建议、依据、置信和不确定项）
  -> 用户接受/修改/拒绝
  -> 正式业务用例与审计
```

- `ModelGateway` 至少支持 `disabled` 和一个兼容 HTTP 供应商；没有模型配置时全部核心功能仍可使用；
- 模型调用不持有数据库事务，慢调用通过数据库任务表运行，首版不新增 Redis；
- 保存模型供应商、模型 ID、参数、提示模板版本、输入记录 ID/摘要、输出、耗时、用量和用户处理结果；不把非确定性模型调用宣称为可重复计算；
- 模型只返回严格 JSON；Schema 失败、超时、限额或内容风险均降级为无建议，不影响正式流程；
- 结构化查询和图谱路径优先于向量数据库。只有实际检索评测证明有必要时再引入嵌入与向量索引。

### 5.2 分阶段门槛

1. **接口和评测集**：定义供应商中立合同、脱敏规则、预算和固定测试样本；
2. **离线影子模式**：模型生成建议但界面不自动采用，比较人工选择、规则输出和模型建议；
3. **显式辅助模式**：用户点击后生成草稿，接受/修改/拒绝均留痕；
4. **有限自动填充**：只填充低风险、可撤销字段，提交前必须确认；
5. **不进入自动执行**：高风险外部动作继续只建议、阻断和留痕。

评测至少覆盖：事实引用正确率、Schema 合格率、人工接受率、错误自信、提示注入、跨记录数据泄漏、中文表达一致性、延迟和单次成本。

## 6. 建议迭代顺序

### 0.2.0-beta.2：事实与低摩擦整改

- 周复盘服务端权威计算与可审计人工调整（VERIFIED，Gitea run 91）；
- 分类输入替代默认数字评分；
- 实际耗时、交付状态、瓶颈变化和证据变化；
- 日常项目上下文复用。

### 0.3.0-alpha.1：标准服务与 Web

- 正式 OCI 基础镜像、独立迁移任务、存活/就绪检查；
- 单节点标准云部署、HTTPS、secret、备份恢复和升级回滚；
- Web PWA 基线和小组件摘要 API。

进度（2026-07-31）：OCI Dockerfile、独立迁移任务、单节点 Compose、安全容器边界和迁移感知的双探针已实现，等待权威 CI 与隔离容器验收；HTTPS、digest 固定、备份恢复演练及 PWA 仍未完成。

### 0.3.0-alpha.2：Windows 小组件验证

- PWA 小组件、Windows 11 真实交互和认证失效验收；
- 根据结果决定是否需要已打包 Win32 provider。

### 0.4.0-alpha：大模型影子模式

- Model Gateway、上下文白名单、严格 JSON Schema、调用审计和评测集；
- 自然语言结构化建议与周复盘草稿；
- 不自动写入、不执行外部动作。

## 7. 本轮不做

- 不恢复完整 Windows/Linux GUI 功能扩展；
- 不实现 PGlite 与 PostgreSQL 离线多主同步；
- 不直接在现有 NAS 生产入口安装证书、修改 Nginx 或重建数据库；
- 不预选云厂商或模型供应商；
- 不让大模型替代确定性规则、用户授权和审计边界。
